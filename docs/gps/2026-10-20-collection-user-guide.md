# 鞋垫与 GPS 同步采集说明（本地实现，待 APK／真机验收）

本说明对应 uni-app `0d35957` 与连接回调修复 `d11fc58`。不是已部署声明。
需要技术人员先部署 GPS 后端、完成005迁移，并重新打包安装手机 App；只更新服务器不能更新旧 APK。

## 一次采集怎样操作

1. 使用采集医生账号解锁，选择本次患者。在“我的”连接鞋垫，返回首页。
2. 首页“同步记录鞋垫与 GPS”选择已连接设备，核对患者和设备后点击“开始同步记录”。
3. 保持 App 前台。此时共同记录窗口同时接收38项步态消息和独立GPS1消息；两者不必同频率。
4. 查看足底压力、IMU和左右脚固件步态值；下方“鞋垫 GPS 原始状态”单独显示定位标记、卫星、HDOP、数据年龄和GPS速度。
5. 完成后点击“停止记录”。如果还有待上传条目，保持原医生登录，检查网络，必要时点“重试上传”。
6. 上传完成后在工作台选择同一患者和对应步态会话，选择“GPS 轨迹与质量”查看。
   该入口已本地交付并通过合成纵向，但当前线上版本尚未更新GPS，需等技术人员完成成套部署。

**连接和实时显示不等于已保存。** 未点击“开始同步记录”时仍可看实时值，但不会通过新采集链路保存。
“正在同步记录”也不等于所有条目都已上传，需要同时看待上传数量和错误提示。

## 数值怎样理解

- GPS原始速度来自鞋垫GPS，单位m/s；左右脚步速来自鞋垫固件，两者分别显示，不相互替代。
- GPS“有效”只是固件fix标记，不是米级精度保证；HDOP越小通常质量越好，但不能直接当作米制误差。
- 无fix／空坐标也保留原始GPS消息，不妨碍步态保存；它们不能作为有效轨迹位置。
- 手机接收时间表示完整一行到达手机的时刻。GPS UTC是另一份原文时间，共同起止窗口不是硬件对时。
- GPS序号可在固件重启后复位；上传使用独立事件身份，不能只凭GPS序号判断重复。
- 一条38项步态消息或一条GPS消息各算1条待上传事件。步态事件在后端保存为L/R两条原始行，不代表丢失另一脚。

## 常见状态与处理

| 页面状态 | 含义及处理 |
|---|---|
| 等待GPS1消息 | 鞋垫尚未发来完整GPS消息；先检查硬件接收，不要把空白当成零位置 |
| 无效／搜星中 | 仍可开始和继续记录，原始GPS保留，待有效定位后再看轨迹 |
| 采集中·等待重新连接 | 采集窗口保留，但缺失期间不补造样本；重新连接原设备，不能把另一设备当作原设备 |
| 已离开前台 | 本次记录已停止，待上传数据保留；回到前台后需重新开始，不承诺后台连续采集 |
| 上传已暂停 | 短暂网络错误会有限重试；仍失败则保留数据，检查网络后手动重试，不无限循环 |
| 请原操作员解锁后重试 | 当前账号不能补传另一医生的记录；回到原医生账号处理，不转移患者归属 |
| 缓存达到上限 | 最多5000待发事件，达到后停止记录且不覆盖旧事件；完成上传后可重新开始 |
| 缓存不可用 | 设备配额或读取／写入失败可能更早停采；保留App和数据联系维护，不先卸载或清缓存 |
| 手机时间回退 | 在最后有效接收时刻停止；校准手机时间后再开始，不改写旧时间 |

切患者、重新启用／解锁操作员、主动断连、关闭蓝牙或删除设备会结束当前窗口，待发记录仍绑定原患者和医生。
App重启不自动继续采集，只尝试保留和补传已持久化窗口；不能据此保证系统杀进程前最后一条一定保存。

## 当前限制

只交付前台采集，不新增手机定位权限／后台服务。已请求采集时屏幕常亮，实际设备行为仍需真机验证。
手机吞吐、原生蓝牙插件、HBuilderX编译、存储配额和弱网长时运行尚未验收。
多设备场景尚有一个显示Minor待整体审查：连接非当前采集设备可能清除等待重连提示，
但固定采集对象和队列不会随之改变；验收时以卡片上的采集设备及真实连接为准。
