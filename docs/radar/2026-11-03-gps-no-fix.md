# GPS 未定位报文修复与交付（F07，2026-11-03）

## 已确认根因

Ru1提供以下实际硬件报文，并要求未定位数据也正常解析、传输和显示：

```text
GPS1,5,0,nan,nan,nan,nan,0,99.99,617,,16607,0
GPS1,6,0,nan,nan,nan,nan,0,99.99,626,,17551,0
```

与定位成功示例不同，fix=0时纬度、经度、海拔、速度使用小写`nan`表示缺失。原手机严格数字解析在第4字段抛错，原后端同样返回400；本地以用户原文复现。七位小数和DOUBLE容量不是这次手机拒收的原因。

## 协议处理

| 项目 | 处理 |
| --- | --- |
| fix=0时lat/lon/alt/speed/hdop的精确小写nan | 接受并映射为null；数据库为SQL NULL |
| GPS原始行 | 不修改，完整保存nan及空UTC，保持审计和同ID重传语义 |
| 旧空字段 | 保留原有null行为 |
| 定位标记、卫星数、HDOP99.99、数据年龄、chars/errors | 按原值保留，作为无效定位状态证据 |
| 手机实时显示 | 解析计数增加，不增加格式拒收；显示未定位/搜星中，缺失速度为— |
| 工作台 | 无效质量计数及原始表保留记录；缺失数值为空，raw_line可见nan，不生成坐标或轨迹 |
| 有效定位与旧38字段 | 保持原严格数字规则，不接受nan、Infinity或部分数字尾随文字 |
| 对时/Agent | 手机接收时间关联不变；GPS原始内容仍不进入模型评分或诊断上下文 |

除以上明确的缺失标记外，不增加宽松parseFloat、自动trim、大小写猜测或全局polyfill。

## 相关MySQL读取修复

核查完整展示链路时，本地实际SQLAlchemy MySQL/PyMySQL dialect结果处理器表明：GPS五个默认DOUBLE读为Decimal，Flask JSON序列化会输出字符串，例如`"99.9900000000"`，工作台严格数字契约将拒绝。

GPS五列模型改为`mysql.DOUBLE(asdecimal=False)`，读取及JSON保持有限浮点数；NULL仍为null，DDL仍为DOUBLE。该改动是ORM读取配置修复，不需要RDS表结构迁移。没有改其他模型列或SQL脚本。
